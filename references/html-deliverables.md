# HTML 交付文档规范 v1

适用于工作台的 PRD、技术、UI、开发、测试、上线六类独立文档。HTML 是统一阅读与版本交付格式；SQLite 中的任务和 Phase 仍是当前事实来源。不要为了排版再维护一份独立事实台账。

PRD 与技术方案必须遵循 [visual-narrative.md](visual-narrative.md) 的图表优先及总—分—总规范；整体、目录和模块都先给结论，展开图表，再收束决策、验收和风险。

## 阅读与版本

- 当前页：`/tasks/<taskKey>/documents/<kind>`，由 SQLite 生成，展示项目、任务编号、负责人、生命周期状态、数据修订号、更新时间及最近变更。
- 评审交付：在相关结构化数据补齐后，用 `workspace document <task-dir> --phase P1 --kind technical --version v0.1` 生成并登记独立 HTML。其他 kind 同理。文件位于 `deliverables/P1/technical/v0.1.html`，CSS 内嵌，可离线阅读；同一版本拒绝覆盖，修订使用新版本号。
- 同一套渲染器服务当前页和版本快照，快照明确注明时点，不能把历史快照当作当前状态。导出不会确认方案、推进阶段或把测试改为通过。
- HTML 使用语义标题、表格、目录或段内锚点、可折叠长细节、响应式和可打印样式。缺失内容写“待补充”；确实不涉及的内容记录 `not-applicable`、理由和依据。不要复制空白表格或生成虚假的 UI 截图来凑数。
- 需求、接口、资源、用例和排期用对象数组表达，渲染为表格；结论用短段落。图示需要时使用自包含 SVG/图片/离线 HTML，保留其来源，不能只放未渲染的 Mermaid/PlantUML 源码冒充图。
- UI 原型另存自包含 HTML 并登记 `kind=ui`；实际页面、空态、加载、失败、禁用、权限及返回路径按需求覆盖。CSS/JS/图片内嵌，不依赖外网 CDN。原型与设计文档分别登记，结构化记录本身不是可操作原型。
- 上线页面的勾选通过工作台接口保存到 SQLite；离线 HTML 为当时的只读结果，不提供看似保存却只留在页面内存的勾选。

## 六类文档

| kind | 文档 | 固定内容 |
| --- | --- | --- |
| product | 产品 PRD | 背景现状、目标与范围、需求与验收、角色/入口/流程、假设与待确认、需求追踪 |
| technical | 技术设计 | 版本、项目背景、干系方、概要设计、详细设计、监控、上线方案、质量保障、排期、沟通 |
| ui | UI 与交互设计 | 适用范围、页面与布局、用户路径、关键交互和异常状态、响应式/键盘可访问性、交互原型与验证 |
| development | 开发记录 | 范围与模块、子任务、分支/SHA、验证、问题与下一步 |
| testing | 测试用例与结果 | 范围/环境/版本、用例、缺陷与回归、需求覆盖 |
| release | 上线资源与检查表 | 发布版本、代码、功能开关、配置中心、网关路由、适用的其他资源、发布/灰度/回滚顺序、执行记录、检查表 |

PRD 每项至少记录编号、优先级、角色/入口、需求描述、业务规则及可核查的验收标准。测试每项记录编号、关联需求、前置条件、步骤、预期、实际、状态、环境/版本和证据。未执行用例不得写 PASS。

## 技术设计参考及字段


现有 `scope`、`artifacts`、`workItems`、`traceability`、`approvals` 保持为对应事实来源。补充章节放到 Phase 的 `documents.technical`（可选字段；按需填充，不要求复制现有字段）：

| 字段 | 内容/表格列 |
| --- | --- |
| versionHistory | 内容、版本、作者、修订时间、详情 |
| projectBackground | 需求名称、需求类型、PRD、任务链接 |
| terminology | 名词、释义、备注 |
| stakeholders | 模块名称、依赖事项、待确认问题、负责人、方案链接、备注 |
| designOverview | 设计思路；图示放现有 architecture/mainFlow/stateMachine 等 artifacts 的 details 或关联 HTML |
| interfaces | 功能、入口、服务/appkey、接口、入参、出参、兼容性；参数另列名称/类型/含义/必填/默认值/备注 |
| configurationChanges | 变更类型（新增/修改/删除）、appkey、key、含义、脱敏后的前后值、环境、影响 |
| dataMigration | 范围、实现方式、前置条件、执行顺序、幂等/重试、校验、回滚、SQL/脚本证据路径 |
| monitoring | 指标、日志、告警阈值、查看入口、负责人；确实不涉及说明原因 |
| rollout | 发布顺序、灰度前/灰度/全量、兼容性与回滚；未另填时复用 artifacts.release |
| qualityAssurance | 检查项、结论（需要/不需要/待评估）、说明、依据；涵盖权限、影响、兼容性、大数据量、并发、幂等、自动化等适用项 |
| schedule | 事项、负责人、起止时间、依赖、状态；与 workItems 已有项关联 |
| communication | 会议/决策时间、参与人、结论、待办、负责人、期限 |

各字段接受简短字符串、对象或对象数组；需要表格时优先使用中文列名的对象数组。技术变更用文字注明新增/修改/删除，颜色只作辅助。质量评估默认待评估，不能照搬参考文档里的“不需要”。

## 上线资源参考及字段


Phase 的 `documents.release` 保存分类资源明细，实际执行仍写 `releases`，用户勾选仍写 `releaseChecklist`，执行前的权限和批准边界维持原有规则：

| 字段 | 资源类型 | 最少内容 |
| --- | --- | --- |
| code | 代码 | 服务、分支、PR、打包/版本、SHA、依赖 |
| featureFlags | 功能开关 | key、配置 URL、描述 |
| configuration | 配置中心 | appkey、配置 URL、key、含义、脱敏 value；测试和生产分开记录 |
| gateway | 网关路由 | 应用、接口/路由、环境、配置入口、变更说明 |
| sql | SQL/DDL/数据迁移（适用时） | 数据库、脚本路径、顺序、数据范围、执行/校验/回滚 |
| scheduledJobs | 定时任务（适用时） | 任务名称、调度、参数、并发/重试、开关 |
| mq | 消息资源（适用时） | topic、生产/消费、权限、积压/重试 |
| permissions | 权限/证书（适用时） | 资源引用、用途、负责人、有效期；不存秘密材料 |
| other | 其他资源（适用时） | 类型、资源、变更与依赖 |
| rollout | 执行计划 | 顺序、动作、前置依赖、负责人、验证条件、回滚步骤 |

每条适用资源再记录资源编号、环境、操作（新增/修改/删除）、负责人、状态、验证证据和回滚。引用同一资源编号到 `releaseChecklist`，不把表格中的计划状态自动当作用户勾选。固定四类资源如果不适用，写有依据的 N/A；SQL/定时任务/MQ 等章节仅在该字段存在时显示。表格为空仅表示待补充，不能视为无变更或已上线。

## 实现与维护

`workspace_documents.py` 定义章节和数据来源，`assets/document.css` 定义文档样式。查看页和版本导出共用这两处。修改格式时同时验证既有 Phase 的兼容展示、文档导出的版本保护、HTML 转义，以及上线勾选的持久化。
